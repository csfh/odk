## Toolchain and commands

Stable Rust (1.96 on the development machine), edition 2024, Linux x86_64 only (ADR 0001, ADR 0002). Inside a Cargo project:

- Build: `cargo build`
- Test: `cargo test` (one test: `cargo test <name>`)
- Lint: `cargo clippy --all-targets -- -D warnings`
- Format: `cargo fmt` (CI-style check: `cargo fmt --check`)
- Benchmark: `cargo bench -p odk-ui` (every component's frame, a page of all of them, scaling, typing and Tab) and `cargo bench -p gallery` (each gallery page); `cargo bench -p odk-ui -- Button` runs those whose names match. They draw on GPUI's test platform, whose text shaping is a stand-in, so they are a floor to compare one change with the last. `tools/idle-cpu [--page ID] [--max PERCENT]` measures the running gallery's CPU while idle on a real renderer, headlessly, and `tools/idle-cpu --all` is the gate (2% idle, 8% with a spinner in view; run it before calling a gallery change done); `tools/visual-scenarios` takes the reference screenshots (themes, densities, corners, focus, a menu) through `tools/headless-shot`, and the gallery reads `GALLERY_DENSITY`, `GALLERY_CORNERS` and `GALLERY_MOTION` as well; `GALLERY_PAGE=<id>` opens the gallery on a page (ids in `docs/gallery.md`) and `GALLERY_THEME=<name or directory>` on a previewed theme, which with `tools/headless-shot` is how to look at a page in another theme (`crates/odk-theme/tests/fixtures/` holds five).

The Cargo workspace is at the repository root (members in its `Cargo.toml`); run the commands there, with `--workspace`. Every crate has the workspace's version (ADR 0064). The checks `main` requires are CI's, and to run them locally: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings`, `cargo machete`, and `GALLERY_FRAME_BUDGET_MS=12 DRAW_BUDGET_MS=30 cargo test --workspace --all-features --locked` (CI's frame budgets; the 4 ms defaults are the development machine's and fail under load).

## Branches, pull requests and releases

- `main` is protected: a change goes in by pull request once `tests`, `msrv`, `audit` and `machete` are green, and is merged with a merge commit, never with `--admin`. A pull request's body has three sections: Summary, Evidence and Merge Danger.
- Commits and tags are GPG-signed; a tag is made with `git tag -s`. If signing fails, ask the owner to unlock the key rather than committing unsigned.
- Before numbering an ADR, look at every branch, not just `main`, since open pull requests hold numbers `main` lacks: `git fetch`, then `for b in $(git branch -r --format='%(refname:short)'); do git ls-tree --name-only "$b" docs/adr/; done | sort -u`.
- No pre-release is cut for now (2026-10-27). To put `main` on the development machine, build the four programs with `cargo build --release --locked -p odk-cli -p oma -p oma-consent -p odkd`, run `tools/package-release target/release <dir> main-<short sha>`, then `ODK_BASE_URL=file://<dir> sh <dir>/install.sh`; `odk --version` still prints the workspace's version. When a release is wanted again, `packaging/README.md` gives the order: the version commit on `main`, then the signed tag. Spikes under `spikes/` are excluded from it, so run their commands inside each spike's directory.

Once built, `cargo test --workspace` takes about two seconds. Any `-p` selection reuses the same GPUI build: every member depends on `crates/deps`, which asks for shared dependencies with the features the whole workspace uses, because Cargo otherwise unifies features only across the packages in one build and a different selection would recompile GPUI. After adding or changing a dependency, run `tools/check-deps` and add whatever it prints to `crates/deps/Cargo.toml`. `odk-ui`'s tests use GPUI's `test-support` feature, so test builds compile a second GPUI once; switching between `cargo build` and `cargo test` reuses both. End-to-end tests run a private copy of `oma` with no `oma-consent` next to it; a test that could reach the real dialog would wait for a click forever.

`GLOSSARY.md` defines the project's terms and `docs/adr/NNNN-slug.md` records every decision. Read both before designing anything, and use the glossary's terms exactly. Record new terms and decisions with the `domain-modeling` skill, as they are settled. `docs/spec/` holds normative specs that fill in details the ADRs leave open (`odk-overlays.md`, `odk-interaction.md`, `odk-db.md`, `manifest.md`, `oma-cli.md`, `sandbox-baseline.md`, `seccomp.md`, `consent-dialog.md`, `plugin-manifest.md`, `odk-theme-tokens.md`, `odk-ui-components.md`, `odk-text-input.md`, `odk-foundation-tokens.md`, `odk-source-palette.md`, `odk-semantic-tokens.md`, `odk-component-tokens.md`, `odk-motion.md`, `component-checklist.md`); an ADR always wins over a spec, and a spec must never quietly change a decision. `docs/plan.md` is the non-normative build order for when implementation starts. `docs/checks.md` lists facts the design depends on that are still unverified; do not assume them. An ADR that replaces an earlier one marks the old one `status: superseded by ADR NNNN` instead of deleting it; one that changes only part of it marks it `status: amended by ADR NNNN`, meaning the rest still holds.

## Windows: headless only

Never open a window on the user's desktop, and never touch their session. This is a hard rule, with no exception for a quick check.

- Do not run anything that opens a window under the user's compositor: no `cargo run -p gallery`, `-p hello` or `oma-consent`, and no `odk oma run` of a GPUI program.
- Do not drive the user's session: no `wtype`, `ydotool` or `hyprctl dispatch`, and no moving focus or creating outputs.
- Do not capture the user's screen: no `grim`, `gpu-screen-recorder` or any other screenshot or recording of their outputs.
- Test behaviour headlessly, on GPUI's test platform (`crates/odk-ui/src/checklist/`). Its fake clock covers animation and timing.
- Visual checks go through `tools/headless-shot`, which runs the program under a private headless sway and takes a screenshot of that display only. It can also send keys there with `--keys`, for example `tools/headless-shot --keys "Tab Tab" target/shot.png -- ./target/debug/gallery`. `wtype` and `grim` are allowed only through it, never against the user's display.

The same goes for the rest of the host: tests work on fakes and throwaway directories.

- Registration stays text in `packaging/`: no `binfmt_misc` entry on the development machine, no write to `/proc/sys/fs/binfmt_misc`, no `systemd-binfmt`, and nothing under `/etc`.
- A test that runs `install.sh` stubs `systemctl` and `update-mime-database` and sets the XDG directories, as `crates/odk-cli/tests/install.rs` does.
- `odk oma mount` acts on the real desktop: udisks attaches a loop device and Omarchy's `udiskie` shows a drive. Its tests use a fake `udisksctl` and a fake sysfs (`crates/oma/tests/view.rs`, the unit tests in `view.rs`). Run it live only with the owner's agreement, and leave no mount or loop device behind.

## Components

Every `odk-ui` component must pass `docs/spec/component-checklist.md`.

- Performance is part of it (items 35 and 36): a component never asks for a redraw while idle or out of view, and has a sample in `crates/odk-ui/src/samples.rs`, which the benchmarks and `checklist/performance.rs` draw. GPUI draws the whole window whenever any view is dirty, and a frame request dirties the view's ancestors too (`docs/checks.md`, "Frame cost"), so animate with a timer at the next visible change, as `Spinner` does, and keep each gallery page small enough to draw well inside a frame. A change that touches how a component draws should be measured with `cargo bench`, not guessed at.

- Read the checklist before building or changing a component.
- A component is done only when it passes every item that applies. Say which items do not apply, rather than skipping them.
- When a built component fails an item, add it to "Known gaps" in the checklist with the item number, and remove the line once it is fixed. Do not call a component done while it has a gap.
- Keep item numbers stable: add new items at the end of their group with the next free number, and leave a gap when one is removed.
- Every component has checklist tests in `crates/odk-ui/src/checklist/`: add the component to `COMPONENTS` in `source.rs` and give it a module of behaviour tests. A known gap is an `#[ignore = "known gap: N"]` test that calls `assert_known_gap`; when you fix a gap, write the real test, drop the `ignore` and remove the row.
- Before trusting a new behaviour test, break the rule it checks once by hand and see it fail.

## Names

The command is `odk oma` (ADR 0056): `odk` is the only program on `PATH`, and it runs the private `odk-oma`, the `oma` crate's binary; the dialog helper is `oma-consent` (ADR 0026, ADR 0033). Errors begin `odk oma:`. ADRs 0001 to 0024 and ADR 0010's title still say `omalaunch`, and ADRs before 0056 say `oma`, since they record decisions as they were made; read either as `odk oma`. Specs and other living documents use the new names.

## What this is

- **ODK** (Omarchy Development Kit): Rust applications with a GPUI user interface and an embedded Luau machine for Plugins. Targets Omarchy (Arch Linux, Hyprland) on Wayland only.
- **OMA** (Omarchy Managed Application): a bundle format inspired by macOS `.app`. The installed Bundle is one `<App>.oma` file (ADR 0052). The code still installs a directory `<App>.oma/` until it catches up. `odk oma` is the program that runs it.

ODK and OMA are deliberately separate: ODK apps can be packaged as Bundles, but `oma` knows nothing about how a Bundle's program was built and does not depend on ODK.

## Decisions that are easy to get wrong

The original brief promised signatures, automatic updates and an "OMA runtime". The ADRs changed that, so do not reintroduce them:

- `oma` has a narrow scope: it verifies, installs, registers, sandboxes and starts Bundles. It does not update applications, host Plugins or compile anything (ADR 0010); `odk oma bundle` assembles a Bundle from an already built executable (ADR 0032). Applications update themselves by staging a new Bundle in their own inbox (ADR 0015).
- A Bundle is signed with ed25519 over one manifest in its prefix (ADR 0060, amending ADR 0007, superseding ADR 0055). The publisher is the pinned root key. The domain is display text and the first-contact host. Release keys are short-lived and rotate under the root. A new root is the first-install consent flow; a rotation is not. Unknown algorithms, a missing pin, a digest mismatch and a parser error fail closed. The code still verifies no signature. There is no "OMA runtime"; the Luau VM and ODK libraries are simply linked into ODK apps. ADR 0054, as amended by ADR 0060, installs the private `odk-oma` binary from a verified file and later from Omarchy's repository. That install is not a runtime that hosts applications.
- ODK depends on nothing a stock Omarchy does not already install (the owner, 2026-10-27): no `erofs-utils`, so `odk-oma` writes and reads EROFS itself (ADR 0067), and no system package for anything else either. Crates are compiled in, and a new one is checked like `ureq` was (ADR 0066).
- v1 supports one program kind, a bundled x86_64 ELF (ADR 0002). The sandbox is built by `oma` itself from namespaces, Landlock and seccomp, deny by default (ADR 0005, ADR 0012).
- Consent is tracked per Identifier in a consent record, so any launch that requests something new prompts, wherever the Bundle came from (ADR 0023). Filesystem grants are limited to six named XDG user directories, looked up in `user-dirs.dirs` at every launch, with no fallback and no arbitrary paths (ADR 0012).
- `oma` is never the parent or an ancestor of an application, not even under `--wait`; an intermediate process starts the init and exits (ADR 0034).
- Each application runs in its own PID namespace under a tiny init, which is `oma` re-executed in an init mode and does only the jobs listed in ADR 0024 (ADR 0024). Do not add policy to it.
- The consent dialog is a separate helper binary, `oma-consent`, run by `odk oma consent` and by `run` and `install` when consent is missing, so `oma` and its init never link GPUI; oma is not a daemon (ADR 0025).
- Applications depend on one `odk` facade crate (`odk::ui`, `odk::theme`, `odk::a11y`, `odk::db` behind the `db` feature, `odk::gpui`) over internal `odk-ui`, `odk-theme`, `odk-a11y` and `odk-db` crates; the components are our own, on GPUI only (ADR 0027, ADR 0028, ADR 0036, ADR 0049).
- Only colours, the user's text size, Omarchy's font and (ADR 0048, accepted; ADR 0046 is superseded) the user's request for reduced motion, which is Hyprland's `animations:enabled`, come from Omarchy, and an application gets all of them from `odkd` (ADR 0062), never from a file or from Hyprland: `odkd` runs as the user outside every sandbox, reads them and writes them to every application that connects to `$XDG_RUNTIME_DIR/odk/odkd.sock`, which oma binds read-only into a sandbox. When Hyprland gives no answer, motion is not reduced. The user's own `[motion] reduced` is ignored. With no `odkd` an application draws the emergency palette at 12 px with motion on. Sizes, radius, border widths and durations are ODK's own, and the text size (`[font] base-size`, `odkd` reads it from `~/.config/omarchy/shell.toml` over the theme's) scales type, controls and spacing but not borders, radii or durations; UI text is set in Omarchy's font unless the application names one (ADR 0035, ADR 0043).
- Plugins run in the application's process, so the Luau sandbox is their only boundary (ADR 0003, ADR 0020).
- GPUI is pinned and wrapped by an ODK UI layer with a raw escape hatch (ADR 0004), but the OMA crates never depend on ODK (ADR 0013).
