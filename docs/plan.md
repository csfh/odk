# Implementation plan

Not normative. This is the order in which to build what the ADRs and specs describe. It decides nothing: if building reveals that a decision is wrong, write a new ADR. Crate names are proposals. Nothing here starts until the user says the design phase is over.

## Before anything

- The user says the design phase is over. CLAUDE.md then loses its no-code rule and gains the build, lint and test commands. Its rule that an ADR wins over a spec stays. Spikes are Rust too, so they wait for this as well.
- Pick the toolchain (stable Rust, edition) and the lint settings.

## Order of work

Each step ends with something that runs and can be tested without the steps after it.

0. **Cheap spikes**, as separate throwaway programs outside the workspace, from `docs/checks.md`: Landlock ABI 6 scoping against the D-Bus abstract socket, the `clone3` and `max_user_namespaces` options for nested user namespaces, `fexecve` re-exec of oma as the init, the Omarchy launcher cache, `mlua` limits on Luau, the theme location. Each result moves its item to Done and updates the ADR or spec it names.
1. **`oma::fmt` and `oma inspect`.** Parse and validate `manifest.toml` exactly as `docs/spec/manifest.md` says; print permissions worded as in `docs/spec/consent-dialog.md`. Tests are Bundle directories, valid and invalid. No sandbox yet.
2. **State, consent record and registration of the Bundle.** `install`, `rollback`, `purge`, the grant file per Identifier, the version rules, the named-directory lookup from `user-dirs.dirs` with its safety rules, and writing and removing the `.desktop` entry, so that `install` does what the CLI spec says (ADR 0009, 0012, 0014, 0023). No path units yet. Non-interactive only: a missing grant fails closed and `--accept-permissions` records one, so this step never has to tell interactive from non-interactive. Needs no GPUI.
3. **Sandbox and init (built, with `oma run` and the parts of step 2 it needs).** Namespaces, mounts from `docs/spec/sandbox-baseline.md`, Landlock, seccomp from `docs/spec/seccomp.md`, the init (ADR 0005, 0024). It must already support what Run once needs, a private tmpfs data directory and no `updates` inbox (ADR 0018), though only the dialog offers it. Test with small purpose-built ELFs that try to break out, then with a real GPUI window, which also settles the GPUI host-library check and the `/dev`, `/run` and `/etc` items. `--wait` lands here. The checks about `/proc` in containers and Arch's user-namespace defaults are answered by running this step on other machines.
4. **Path units and upgrades.** The `systemd --user` units, `--register` as the reconcile, inbox staging, move-then-validate, and the running-app-during-upgrade check (ADR 0009, 0015).
5. **Consent dialog helper (built).** `oma-consent` in GPUI, per `docs/spec/consent-dialog.md`, including Run once, last because it is the heaviest dependency and steps 1 to 4 do not need it. First write the request and answer format into that spec (ADR 0025). Then oma gains the code that runs the helper. Non-interactive mode may need no separate detection: if the helper cannot start or fails, oma fails closed. Confirm that before closing the CLI spec's open item.
6. **Electron check**, then any seccomp changes it forces.

The PipeWire playback-only check is not needed for v1. It only matters if a separate microphone permission is proposed later (ADR 0012).

The ODK crates are a second track and can start after step 0: the Luau host and Plugin loader first, since the `mlua` spike decides its shape, then the UI layer and theming. Nothing in the OMA track waits for it, and a real ODK application is the best test for step 3 once it exists.

## Design language migration

Not normative, like the rest of this file. It plans the move to the four token layers of ADR 0040, which was `proposed` until the user's brief for the button redesign accepted it on 2026-10-22 (step 7). Audited on 2026-10-21 against GPUI 0.2.2, Rust 1.96. The work is done (step 10); read this section as history, and `docs/design-language.md` for what exists.

### How ODK styles things today

- `odk-theme` (no GPUI) reads `colors.toml` into a `Palette` (`palette.rs`, step 1) and builds one flat legacy `Tokens` from it and an optional `shell.toml` in `Tokens::from_palette` (`load.rs`): surface, text, accent, status (with tint and ink), border, control states, space, font, radius, motion. Lengths and durations are constants at the top of `load.rs`. `color.rs` has sRGB `Color` with exact 8-bit parsing, alpha blending, `mix` and WCAG contrast; `oklch.rs` (step 2) adds OKLab and OKLCH.
- `ThemeManager` (`manager.rs`) loads a `ThemeSource` (`discovery.rs`), keeps the last theme that loaded and publishes an immutable `ThemeSnapshot` (Palette, legacy tokens, semantic colours that passed the component checks, generation) only when it changed. `odk-ui` keeps that snapshot, its tokens and its component tokens in one process static (`theme.rs`), not a GPUI global; `run` follows the current theme with a `ThemeWatcher`, reloading on GPUI's background executor and calling `cx.refresh_windows()` on a change. Components call `tokens()` inside `render` and convert with `colour()`. The application's reduced motion is applied to the tokens as they are published.
- No component holds a literal colour (the only one is `TRANSPARENT` in `button.rs`) or a literal radius (17 sites read `t.radius.*`). Sizes are named constants (`switch.rs`, `dialog.rs`, ...). Control height is not a value: it comes out of font size, padding from `Size {Sm, Md, Lg}` and the border.
- Hover, pressed and focus styling is written inline in each component (about 37 `.hover`, `.active` and `.focus` sites). Only `focus_handle`, `focus_layer` and the roving-focus helpers are shared.

### Findings

Constraints and risks, each with what it changes in the design:

1. **The numbers conflict with ADR 0035.** Radius 0 and 120/200 ms are normative today; ADR 0040 proposes 0.8 px, 140/180/240 ms. Code and spec must change together, after acceptance.
2. **`Size` against density.** `Size` is per instance (Button, Input, Select, Textarea, Spinner, InputGroup) and sets padding and font. Density sets control height (28, 34, 40) for the application. One must not replace the other without a decision (see "Open questions" below).
3. **`Variant` is shared and exhaustive.** `Variant {Primary, Secondary, Ghost}` is also used by Badge, Alert, Toast and the overlay. Eight button variants either break downstream `match` and force those components to handle them, or need a separate `ButtonVariant`, or `#[non_exhaustive]` first.
4. **`Tone` has four roles; the design has six.** `Tone` (info, success, warning, danger) lacks accent and neutral.
5. **The 2 px focus indicator against checklist item 32.** Today's ring is the 1 px border recoloured, so it moves nothing. A wider border would move layout; a 2 px ring needs an absolutely positioned layer, as `focus_layer` already does for composite parts.
6. **No keyboard-only focus in GPUI 0.2.2.** There is no focus-visible style (checked in the crate source), so a ring that shows for the keyboard but not for a click needs ODK's own tracking. Focus already coexists with hover and press, since they are separate styles.
7. **Motion is linear.** `Presence::value` in `overlay.rs` has no easing. The curve needs a pure `fn(f32) -> f32` (GPUI's `Animation::with_easing` takes such a function), testable without a window.
8. **One resolution path.** `set_reduced_motion` clones `Tokens` and patches it. Density, radius choice and reduced motion must all go through a single `Theme` build, on reload and on a setting change, or two paths will drift.
9. **`Tokens` is public API** (`odk::theme::Tokens`, `odk::ui::tokens()`) with public fields. It stays until the last step.
10. **`shell.toml` is a colour source today** (control fills, borders, alphas). The brief names `colors.toml` as the only source (see "Open questions" below).
11. **Gallery coverage.** The gallery hand-checks (items 3, 4, 5, 11, 18, 19, 23, 24, 28, 29 of the checklist) cannot be done headlessly for new states.

Not problems: no cycles (`odk-theme` has no GPUI; `oma` and `oma-consent` do not depend on ODK, and `oma-consent` keeps its own `colors.toml` reader on purpose, ADR 0013 and ADR 0025); the static store with `refresh_windows` already gives caching, invalidation and live theme switching; `TYPEAHEAD_RESET` in `select.rs` is behaviour, not motion; the named size constants satisfy checklist item 2, though those that depend on density will need to follow it.

### Target layout

All new logic goes in `odk-theme`. No new crate and no new dependency. Only the `odk-ui` rows below touch GPUI.

| Layer or job | Module | Notes |
|---|---|---|
| Source: load and validate | `palette.rs` (built) | `Palette` from `colors.toml`, moved out of `load.rs`; Omarchy's eight short names, the named-key errors (`docs/spec/odk-source-palette.md`). |
| Source: find, keep, replace | `discovery.rs`, `manager.rs` (built) | `ThemeSource` (current, named, directory), `ThemeManager` and `ThemeSnapshot` with a generation, the fallbacks of ADR 0041, `ThemeDiagnostics`. |
| Colour maths | `color.rs`, `oklch.rs` (built) | OKLab and OKLCH, gamut mapping by chroma, CIE L*, apparent distance, contrast of what is drawn (WCAG ratio kept). Pure. |
| Foundation | `foundation.rs` (built) | `Density`, `CornerRadius`, border and focus widths, type roles, spacing, layout spacing, motion and the easing curve, from a `FoundationConfig`. Constants are ODK's own (`docs/spec/odk-foundation-tokens.md`). |
| Semantic | `semantic.rs`, `resolve.rs` (built) | `Role` x `Emphasis` x `State` to a `Treatment` (background, foreground, border), with surface, text and border tokens. The resolver takes a `Palette` and `ResolveOptions` and returns the tokens and a `Report`; it ranks candidates lexicographically by contrast, hue family, change and priority, and leaves a monochrome palette monochrome (`docs/spec/odk-semantic-tokens.md`). Published in `ThemeSnapshot`. |
| Component | `component/` (built) | `ComponentTokens` over the semantic and foundation snapshots: one lookup per component group (`button(appearance, density, layout, states)`, ...) returning a typed style; colours are `ColourRef`s into the semantic layer, geometry follows from the foundation, `States` decides precedence, `validate` checks every pair, `diagnostics` lists every style (`docs/spec/odk-component-tokens.md`). Strongly typed; no string lookups. |
| Configuration | `config.rs` | `ThemeConfig`: density, radius choice, reduced motion. Per-application overrides, applied in one place. |
| Assembly and cache | `theme.rs` | `Theme::build(&Palette, &ThemeConfig)`. The semantic layer is cached by palette and mode, so a density change recomputes geometry only. Also builds the legacy `Tokens` until it is removed. The component half is done without it: `ComponentTokens::new` shares the snapshot's semantic colours and the foundation's snapshot, so nothing is cached twice; what is left is deriving the legacy `Tokens` from the new layers. |
| Watching | `watch.rs` (built) | Recursive under `current/`, without following symlinks, so edits inside the theme are seen; `follow` watches any `ThemeSource`. |
| GPUI integration | `odk-ui/src/theme.rs`, `layout.rs` | Holds the `ThemeSnapshot`, its tokens and the component tokens in one slot (steps 1 and 5); `components()`, `tokens()`, `theme_snapshot()`, `reload_theme` and `theme_diagnostics` exist. `colour()` stays the only conversion to GPUI, used by `StyledExt::treatment` and `control_geometry`. |
| Shared interaction | `odk-ui/src/interaction.rs` | One helper that applies hover, pressed and focus from a component style, replacing the inline sites. Keyboard-focus tracking lives here. |
| Components | `odk-ui/src/*.rs` | Migrated one at a time, Button first. |

### Order of work

Each step compiles, passes `cargo test --workspace` and changes nothing visible, except the one marked.

1. **Source layer (done, 2026-10-22).** Larger than the first plan's "split `load.rs`", because the user's brief asked for the whole source layer: `Palette` in `palette.rs` with every `colors.toml` key, required and optional, and exact colours; discovery of the current, a named and an explicit theme; `ThemeManager` with snapshots, generations, change detection and diagnostics; a recursive watcher; the store in `odk-ui` holding the snapshot; and ADR 0041, which replaces `run`'s panic with the last good theme and an emergency palette. `docs/spec/odk-source-palette.md` is the spec. Legacy tokens and every test are unchanged, except that a malformed colour and a bad mode are now `Error::BadColor` and `Error::BadMode` instead of `BadValue`.
2. **Colour maths (done, 2026-10-22, with step 4).** OKLab, OKLCH, gamut mapping and the contrast of composited colours in `color.rs` and `oklch.rs`, with round-trip and published-value tests. Written in the crate rather than taken from a colour library, since the workspace has none and this plan adds no dependency. One finding changed the maths: OKLab's lightness overstates differences near black, so perceptual steps use CIE L* for lightness (`docs/spec/odk-semantic-tokens.md`, "Perceptual measures").
3. **Foundation tokens (done, 2026-10-21).** `odk_theme::foundation` and `docs/spec/odk-foundation-tokens.md`, with the easing curve. This differs from the first plan, which gave the foundation today's values: the user asked for ADR 0040's values, so the foundation holds those and nothing draws it, while `Tokens` keeps ADR 0035's sizes and durations and stays the only thing components draw until step 7. In `odk-ui`, the store holds the foundation snapshot beside `Tokens`; `configure`, `set_reduced_motion` and theme reloads go through one path, which sets `Tokens.motion.reduced` from the foundation. That is the store half of step 5. The monospace family is the one foundation value drawn today, and only when an application names one. The gallery screenshot is unchanged.
4. **Resolver beside the legacy mapping (done, 2026-10-22).** `semantic.rs` and `resolve.rs`, tested on every stock theme in `/usr/share/omarchy/themes`, the fixtures and two monochrome palettes: 4.5:1 for text, 3:1 for essential non-text, no new hue. Nothing draws from it yet, and the legacy tokens are unchanged. Larger than first planned, because the brief asked for it:

5. **`Theme` and the store.** One `Theme::build` for the colour layers; reload, `set_reduced_motion` and density already share one path (step 3). `tokens()` still returns the legacy shape, derived from `Theme`, so there is one resolution path from here on.

Colours are references into the semantic layer, checked with every resolution, so a failure is a failed reload; geometry follows from the foundation, which gains `focus_offset` and `thumb_gap`; the semantic layer gains `surface.scrim`. The store publishes them with the snapshot (`odk::ui::components()`), and `StyledExt` gains `treatment` and `control_geometry`. `From<Variant> for ButtonVariant` and `BadgeAppearance`, and `From<Tone> for Role`, map today's enums; `Tone::mark` reads the status marks. 6. **Shared interaction helper (done, 2026-10-22, with step 7).** `odk-ui/src/interaction.rs`: `pointer_states` (the resting, hover and pressed treatments, carrying the element's text style, since GPUI replaces a refined text style whole), `focus_ring` (finding 5: a layer outside the control that takes no space, with the control's corners) and `progress` (a transition the component's own state drives, on the foundation's motion). ### Open questions

Settled by the user on 2026-10-21 and recorded in ADR 0040: `Size` stays and may act differently under each density; 0.8 px is literal (replaced by 2 px on 2026-10-22, ADR 0042, once a 0.8 px corner was drawn and could not be seen); ADR 0040 stays `proposed` until step 7, which accepts it and amends ADR 0035 with the code (done on 2026-10-22); button variants are a new `#[non_exhaustive] ButtonVariant`, with `Button::variant(impl Into<ButtonVariant>)` and `From<Variant>` so existing calls compile, and `Variant` stayed for Badge, Alert and Toast until step 9, which removed it (Alert and Toast had stopped using it, Badge has `BadgeAppearance`).

Open from step 7: whether `Size` as a step from the density (`Md` the density, `Sm` and `Lg` one step either way) is what the user wants; it is *provisional* (`docs/spec/odk-component-tokens.md`, "Geometry"), and the form controls now read it the same way. Whether the ring should show for keyboard focus only (finding 6).

Open from the form controls (`docs/spec/odk-component-tokens.md`, "Open questions"): a field action's padding and inset, and the `!` that marks a wrong field, check box or radio group.

Open from navigation and feedback: the provisional `motion.cycle`, a status dot's 8 px, a progress bar's 4 px, a compact alert's padding and a text skeleton's last line (`docs/spec/odk-component-tokens.md`, "Open questions"); whether a skeleton should pulse, which would need a loop of its own; and pagination, when something needs it.

Open from the component layer (`docs/spec/odk-component-tokens.md`, "Open questions"): the provisional `focus_offset` and `thumb_gap`, menu items as high as a control, and whether a tooltip is the inverse surface.

Open from step 4 (`docs/spec/odk-semantic-tokens.md`, "Open questions"):
- whether a focus indicator must reach 3:1 against the solid fill it surrounds, or a gap of the surface is the rule (finding 5);
- where an application's colour options live, if not in its code;
- the values marked provisional there: the perceptual steps, the 30° hue family, and disabled text's 2:1 floor.

Still open, besides the values `docs/spec/odk-foundation-tokens.md` marks provisional (the control gap, letter spacing, which marks use `radius.small`) and where the legacy timings `cycle`, `hover_open`, `hover_close` and `toast` belong: (1) whether a `shell.toml` that a theme ships itself is used, since the user allowed it "if it's written by Omarchy", and whether `odk-theme` can tell the two apart (the current spec reads either); it shapes step 4. (2) How `Size` acts under density: done at step 7 as that example suggested, and *provisional* (above).
