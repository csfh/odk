# oma command-line specification, version 1

Normative. This spec defines the whole command-line surface of `odk oma` (ADR 0010, ADR 0056). It is deliberately small. It must not change a decision recorded in an ADR; if it needs to, write a new ADR first. Where the two disagree, the ADR wins.

The command a person types is `odk oma`. The private binary is `odk-oma`, at `/usr/lib/odk/odk-oma` or `~/.local/lib/odk/odk-oma`, and it is not on `PATH` (ADR 0056). There is no `update`, `list` or `uninstall` of a Bundle. `odk-oma` does not compile applications or update them (ADR 0010), and uninstalling an application is deleting its `<Name>.oma` file (ADR 0009, ADR 0052). It can assemble a Bundle from a built executable (`bundle`, ADR 0032) but never builds the executable. `odk oma self-upgrade` and `odk oma self-uninstall` replace or remove the odk runtime itself (ADR 0054, ADR 0060). They do not fetch or remove Bundles. The commands below are the accepted surface. The built binary still takes a Bundle directory for every command but `install` and `run`, which also take a Bundle file. `run` runs an installed one, by path or app id, from a read-only tmpfs at `/app`, with no network. `install` at first contact with its publisher's root it verifies the file, fetches `oma-keys`, asks Install or Cancel and installs it. Under a root that is already pinned it says that is not built yet (issue #14). The rest changes to follow ADR 0052 and ADR 0060.

The command a person types is `odk oma …` (ADR 0056). `odk` is the only command on `PATH`: a small dispatcher, crate `odk-cli`, that finds `odk-oma` in `/usr/lib/odk/` or `~/.local/lib/odk/` and replaces itself with it. The program behind it is `odk-oma`, the crate `oma`'s binary, which is private; its messages begin `odk oma:` and its help is titled `odk oma`. With one argument that is a regular file, `odk-oma` is the entry the kernel uses for a `.oma` file (`packaging/binfmt.d/odk.conf`): it seals a copy, checks the envelope against itself, then reads the image (`docs/spec/oma-image.md`), and refuses the file whatever those say, naming the application when both hold and the reason when one does not, until its publisher can be checked and consent asked (ADR 0060, issues #13 and #14). No byte of it is executed.

## Commands

| Command | What it does |
|---|---|
| `odk oma run <target>` | Runs a Bundle in its sandbox and returns once the application has started; setup errors are reported before it returns. If the Bundle requests anything missing from its consent record (ADR 0023) it asks first: a Bundle opened from outside `~/Applications` and not installed gets Install, Run once or Cancel (ADR 0018), anything else Allow or Cancel. Install copies it and runs the installed copy; Run once runs it with a private data directory and records nothing. Fails closed if the dialog cannot run. Used by `.desktop` entries and by Flea. |
| `odk oma run --wait <target>` | The same, but `odk-oma` stays (never as the application's parent, ADR 0034), relays SIGINT, SIGTERM, SIGHUP, SIGQUIT, SIGCONT, SIGUSR1, SIGUSR2 and SIGWINCH, and exits with the application's status (ADR 0024). Ctrl-Z is not relayed yet: it stops `odk-oma` but not the application (`docs/checks.md`). |
| `odk oma install <file>` | Copies a Bundle into `~/Applications` (ADR 0018), asking Install or Cancel first if it requests anything its consent record lacks, or if its publisher root is not pinned for that app id (ADR 0060). It does not yet write a `.desktop` entry and refuses an application whose monotonic version is lower than the stored high-water mark, or equal when the payload digest differs. |
| `odk oma install --accept-permissions <file>` | The same, recording consent for exactly the permissions the Bundle requests now, without a dialog (ADR 0016). A new publisher root is not accepted this way, and a confusable-host warning is not skipped. |
| `odk oma dev [<project-dir>] [--wait]` | For a project under development (ADR 0051): runs the `build` commands of `<project-dir>/oma.toml` (default the current directory), assembles the Bundle as `bundle` does, asks Install or Cancel if it requests anything its consent record lacks, stops the daemon of the installed copy it replaces, installs over that copy and runs it as `run` does. A failed build or a Cancel changes nothing. |
| `odk oma rollback <identifier>` | Swaps the current and previous versions (ADR 0011). It does not lower the high-water mark (ADR 0060). |
| `odk oma purge <identifier>` | Deletes the application's data, previous version, inbox, held upgrade, consent record and high-water mark for that publisher root and app id. |
| `odk oma bundle <executable> --manifest <manifest.toml> [-o <dir>] [--include <file>[=<path>]]... [--sign <secret-key>]` | Assembles `<Name>.oma` in `<dir>` (default the current directory) from a built executable and a Manifest, validates it and prints its path (ADR 0032, ADR 0052). `--include` may be repeated. `--sign` fills the manifest signature with the release key (ADR 0060). |
| `odk oma consent <target>` | Shows the consent dialog for a Bundle through `oma-consent` (Allow or Cancel) and records the answer in its consent record; says so and opens nothing if there is nothing to ask. The same step `run` and `install` take when something is missing (ADR 0033). A new publisher root uses Install, Run once or Cancel (ADR 0060). |
| `odk oma inspect <file>` | Prints the Bundle's name, Identifier, semver, monotonic version and the permissions it requests, worded as in `consent-dialog.md`. Also the publisher host, the root fingerprint, and a held file signed by a different root if there is one (ADR 0060). When a pinned host does not resolve, it says the name may have been lost. |
| `odk oma mount <file>` | Mounts a Bundle file read-only and `noexec`, as the desktop mounts a disk image, through udisks, and prints the directory (ADR 0053, ADR 0065). A view of the same file, by device and inode, is used again, whoever made it. Refuses a file that is not `OMA1` and an EROFS image, and works only from the active desktop session. |
| `odk oma mount --open <file>` | Mounts it and opens that directory in the file manager. |
| `odk oma mount --unmount <file>` | Unmounts every view of that file and deletes its loop devices. A view otherwise lasts until it is ejected or the machine stops. |
| `odk oma --register` | Reconciles `~/Applications` and the inboxes: generates and removes `.desktop` entries, activates upgrades and enables or disables inbox watches. Idempotent. Used by the path units and the login run (ADR 0009, ADR 0015). It does not open the consent dialog. |
| `odk oma self-upgrade` | Replaces `odk-oma` and the rest of that runtime with a newer release whose signature verifies under the release root compiled into the running binary, and whose monotonic version is above the high-water mark in the receipt (ADR 0060). A different release root is not accepted. Refuses when pacman owns the files. |
| `odk oma self-uninstall` | Removes the odk install and leaves application data (ADR 0054). Refuses when pacman owns the files. |
| `odk oma --init` | Internal. Runs the init inside an application's PID namespace (ADR 0024). Not for users and not a stable interface. The init is a re-exec of `odk-oma`. |

## Targets

`<target>`, for `run`, is either a path to a Bundle file or an Identifier. An argument that is a valid Identifier (see `manifest.md`) is treated as an Identifier and looked up among installed Bundles; anything else is treated as a path. Identifiers cannot contain `/`, so a path with a slash is never mistaken for one.

## Behaviour

- **`install`** refuses a Bundle whose monotonic version is lower than the high-water mark for that (root key id, app id), and refuses the same version when the payload digest differs (ADR 0060). The only way to run an older installed copy is `rollback` (ADR 0011), which does not lower the mark.
- **`rollback`** fails if there is no previous version.
- **`purge`** refuses while the Bundle is still in `~/Applications`, since deleting its consent record would only make it ask again; remove the Bundle first.
- **`bundle`** takes the Bundle's name from the Manifest's `name`, with `/` replaced by `-`. It stages the Manifest unchanged, the executable at the Manifest's `executable` path with mode 0755, the icon if the Manifest names one, and each `--include`. It runs `mkfs.erofs` as ADR 0052 specifies, stamps the preamble, validates the result as `inspect` does, and renames it into place; if anything fails, nothing is left behind. It refuses to replace an existing `<Name>.oma`.
- **A different publisher root** is not installed by `--register`. The file is held at `~/.local/share/oma/held/<root-key-id>/<app-id>.oma`. The first-install dialog is how a new root gets in, and a stored denial is not asked again by a retry (ADR 0060). `--accept-permissions` does not stand in for that dialog. A file already in hand that verifies under the pinned root, with a higher version and an unexpired manifest, is applied even when the publisher host cannot be reached. A file that does not verify, a lower version, and an expired manifest are deleted.
- **Launch** of an installed file that still verifies under the pinned root proceeds with no network, including when the manifest has expired and when the publisher host does not resolve. NXDOMAIN on a pinned host is reported as a suspected loss of the name. Updates that have to be fetched wait (ADR 0060).
- **`dev`** is the one command that replaces an installed Bundle (`install` still refuses one). Its `oma.toml` (ADR 0073; `dev.toml` before it, which is refused with a request to rename it) is read from the project's directory and is never put in the Bundle; a Manifest key in it is refused as belonging in the manifest. Keys: `build` (an array of commands, each an array of strings, run in order in the project's directory, stopping at the first failure; may be empty), `executable` (required: the built program, as `SOURCE` or `SOURCE=DESTINATION`; it is copied to the Manifest's `executable` either way, and a `DESTINATION` that is any other path is refused before anything is built), `manifest` (default `manifest.toml`) and `include` (as `bundle --include`). Every path is relative to the project's directory, and may go above it. Any other key, an empty command and a missing file are errors. The order is: read, build, assemble, ask, stop the daemon, install, run; the daemon is the unit `run` would start (`oma-<Identifier>`), stopped only if the Manifest declares one. If something else still accepts connections on its socket, `dev` says so on standard error and goes on.
- **Fail closed:** if the dialog cannot give one offered answer (no display, no `oma-consent` next to `odk-oma`, a non-zero exit, or output that is not one offered word), nothing is granted, installed or started, and the error names `odk oma install --accept-permissions` as the dialog-less way (ADR 0016). An unknown algorithm, a missing pin, a digest mismatch or a parser error is also a hard failure (ADR 0060).
- **Order:** `run` applies its refusals (`dbus`, a kernel without Landlock ABI 6 for `network`) before asking, so nobody consents to something that cannot start.
- **`inspect`** validates the Manifest and exits non-zero if it is invalid.
- **Exit status:** zero on success and non-zero on any failure or when the user cancels the dialog. Under `--wait`, the application's own exit code is returned instead (ADR 0024).
