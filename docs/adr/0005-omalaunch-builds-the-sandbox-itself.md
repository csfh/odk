# omalaunch builds the sandbox itself from the manifest

omalaunch isolates each launched application using Linux mount, user, PID, IPC and network namespaces combined with Landlock and seccomp, configured from the permissions declared in the Bundle's manifest on top of the baseline in ADR 0012. It does this directly rather than shelling out to `bwrap` or delegating to Flatpak and portals. Permissions are deny-by-default and shown to the user for consent (ADR 0023). We chose this over Landlock alone (weaker isolation, no network namespace) and over Flatpak (brings its own packaging and runtime model, which conflicts with `.oma`).

The PID namespace was briefly dropped because it conflicted with omalaunch `exec`ing the application (ADR 0017); it is back, and the application runs under a tiny init (ADR 0024). Landlock's signal scoping may be added as a second layer; it needs Landlock ABI 6. The development machine (Linux 7.2.8) has Landlock in its active security modules and reports ABI 10, so it is available there. Which kernel first shipped ABI 6 is unconfirmed, so omalaunch must check the ABI version at runtime and not assume it.

An application with `network = true` shares the host's network namespace (ADR 0012), where abstract unix sockets live, including D-Bus's abstract address, and a private `/run` does not hide those. It could therefore reach the session bus without a `dbus` permission. For such applications omalaunch requires Landlock's abstract-unix-socket scoping (ABI 6) and refuses to launch them on a kernel that lacks it. Applications without network get a fresh network namespace that already isolates abstract sockets, so they need no scoping. Every application also gets a private IPC namespace, so SysV shared memory and message queues are not shared between applications.
