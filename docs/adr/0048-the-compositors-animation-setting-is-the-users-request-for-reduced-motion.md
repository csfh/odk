# The compositor's animation setting is the user's request for reduced motion

ADR 0046 had ODK read `[motion] reduced = true` from the user's `shell.toml`, a key of ODK's own, because a probe on 2026-10-23 found no Omarchy setting for it. On 2026-10-24 the user said ODK must follow the system's reduced motion, font, text size and theme, and only from Omarchy's own canonical settings. Looking again in the canonical install (`/usr/share/omarchy`, 4.0.0.alpha): Omarchy defines no accessibility setting and no command for motion, and one place for it, Hyprland's own `animations.enabled` (default `true` in `default/hypr/looknfeel.lua`; the user template `config/hypr/looknfeel.lua` documents `hl.config({ animations = { enabled = false } })`, "Disable all animations"). Atmos's Animations row edits the same key; Atmos is not canonical, and ODK does not read anything of it. So **the user asks for reduced motion when Hyprland's `animations:enabled` is false**, and ODK reads it from Hyprland, not from a file: Hyprland's IPC at `$XDG_RUNTIME_DIR/hypr/$HYPRLAND_INSTANCE_SIGNATURE/.socket.sock`, the request `j/getoption animations:enabled`, whose reply carries `"bool": true` or `false`. It follows the setting on `.socket2.sock`, which announces `configreloaded>>` when Hyprland reloads its configuration (it does so by itself when the file changes), by reading it again.

The compositor is authoritative whenever it answers. When it does not (no Hyprland, no socket, a reply that is not understood, a query that takes longer than a moment), the user has not asked, and motion is not reduced. The `[motion] reduced` key in the user's own `~/.config/omarchy/shell.toml` is never a source, not even then: ADR 0046 is superseded. A sandboxed application cannot reach Hyprland and must not, so it gets no answer and does not reduce motion. This record first gave it a copy of the answer, a `[motion] reduced` key in oma's copy of `shell.toml`, read where `OMA_SANDBOX=1`; on 2026-10-25 the user removed that, because the sandbox is to be told by a source on the host side that is yet to be decided, and a stopgap would have to be taken out again. Until then a sandboxed application is told nothing. The application's own choice (`odk::ui::set_reduced_motion`) is unchanged and still adds to the system's. The user accepted this on 2026-10-25.

## Considered Options

- **Parse `looknfeel.lua`.** Works with Hyprland not running, but it is a Lua file with `require`s, toggles and a user's own edits, so a parser would answer what the file says, not what Hyprland does.
- **`hyprctl` as a subprocess.** The same answer, and what `oma-consent` uses; but a process for every reload, and its output is another format to parse. The socket is a plain request and a short reply.
- **GNOME's `enable-animations` and the freedesktop portal.** ADR 0046's reasons stand: nothing in Omarchy sets them.
- **Keep `[motion] reduced` as a user setting beside Hyprland's.** Two answers to one question, and the user's rule is one canonical source.

## Consequences

- A user who turns off Hyprland's animations gets reduced motion in every ODK application on the next configuration reload; one who turns them back on gets it back. `hyprctl keyword animations:enabled` changes the setting without a `configreloaded`, so ODK learns of it at the next reload of anything it watches; Omarchy's documented way, editing `looknfeel.lua`, reloads.
- Hyprland's setting is about window animations, not about what a user's accessibility needs, and ODK takes it as that request because it is the one Omarchy has. A user who wants window animations on and reduced motion in applications has only the application's own switch. The `[motion] reduced` key in the user's own `shell.toml` is ignored whether or not Hyprland answers.
- A sandboxed application never reaches Hyprland, and must not: the socket accepts `dispatch`, so an application that could open it would not be sandboxed. The sandbox builds its own `/run/user/<uid>` and mounts nothing of `hypr` there (a test holds this). It is told nothing, so its motion is not reduced on the user's behalf until a source on the host side exists. The application's own switch still works in it.
- The Hyprland instance is found from `HYPRLAND_INSTANCE_SIGNATURE` when set, and otherwise, or when that instance does not answer, as the newest directory under `$XDG_RUNTIME_DIR/hypr` with a socket that does. A systemd user service does not always have the variable, and a process that outlives a restart has the old one.
- A compositor that restarts is followed. When the event connection ends ODK reads the setting again and looks for an instance again, with a wait that doubles from 200 ms to 5 s, and reads again when it finds one; an application that starts while the compositor is not up yet, in a session that has a `hypr` directory or names an instance, does the same. While the compositor is silent its last answer stands, so a restart changes nothing the user sees, and the new instance's answer is taken when it comes. A session of another compositor has no `hypr` directory and is never looked for; an application started with no answer ever does not reduce motion.
- ADR 0046 is superseded. Its reader of the user's own file does not stay. Its copy of the key into the sandbox does not stay either, and `oma` reads nothing from Hyprland. Its finding that Omarchy has no such setting was wrong in the sense that the setting existed under another name. ADR 0044 is unchanged: the sandbox copy holds `[font] base-size` and no motion key.
