# A Bundle may declare one daemon, which runs outside the sandbox

The user asked on 2026-10-24 that Atmos be packed as an `.oma` Bundle, with its backend `ratmos` inside it. Atmos is a window over one daemon (`ratmos daemon`): the window shows what the daemon reports and sends it typed requests over a socket, and the daemon runs `omarchy`, `hyprctl`, `systemctl` and `sudo` for it. The window can live in the sandbox. The daemon cannot: it needs the user's session, their home and their tools, which is what the sandbox exists to withhold. The user also said the daemon must not run twice and that the manifest "should simply declare the daemon". This record is the choices made on their behalf, and is open to change.

**The declaration.** An optional `[daemon]` table in `manifest.toml`:

```toml
[daemon]
executable = "bin/ratmos"
args = ["daemon"]
socket = "atmos/ratmos.sock"
```

`executable` is a path inside the Bundle, held to the rules of the Manifest's own `executable`: relative, no `..`, a regular executable x86_64 ELF, and not a symlink. `args` is a list of strings (none by default). `socket` is a path under the user's runtime directory (`$XDG_RUNTIME_DIR`) where the daemon listens and the application may connect; it is relative, has no `..`, and its first component may not begin with `hypr`, `wayland`, `pipewire`, `pulse`, `bus`, `dbus`, `systemd`, `gnupg`, `sway`, `niri` or `ssh`, which are other things' (the Hyprland command socket is never granted, `docs/spec/sandbox-baseline.md`). Any other key in the table is an error, as everywhere in the Manifest. A Bundle has at most one daemon.

**Consent.** A daemon is a permission, the largest one: a program of the Bundle's runs with the user's full access and no sandbox. The consent dialog says so in one line (`docs/spec/consent-dialog.md`), and the record keeps the executable, the arguments and the socket together, so a change to any of them asks again (ADR 0023). An application that declares no daemon has no new line, and a record written before this one loads as granting none.

**What `oma run` does.** After consent and before it starts the application, `oma run` makes sure the daemon is there:

1. If something accepts connections on the socket, nothing is started. It may be a daemon an installed unit of the application's own started, and a second one must not run (the user's rule).
2. Otherwise `oma run` starts one transient systemd user unit named for the Identifier, `systemd-run --user`, with the socket as a socket unit of its own (`--socket-property=ListenStream=`), so that systemd owns the socket, which is meant to keep one file across the daemon restarting (a bind mount pins a socket's inode, so a daemon that binds its own again would strand a running application; that was not measured, `docs/checks.md`), and with an allowlisted part of the user's session environment (`PATH`, `WAYLAND_DISPLAY`, `HYPRLAND_INSTANCE_SIGNATURE`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR`, `XDG_CURRENT_DESKTOP`, `XDG_SESSION_TYPE`, `LANG`) set on it. The daemon is therefore not a child of `oma` (ADR 0034), `oma` is not a daemon (ADR 0025), and the daemon is started on the host side, never by the init (ADR 0024). The daemon outlives the application and `oma run`; `oma` does not stop it.
3. **Only the installed copy runs a daemon.** The consent record covers the program the user installed, so `oma run` starts a daemon only for the Bundle that `oma` has installed under that Identifier (its canonical root is the installed one's), and refuses any other copy, such as one the application wrote into its own data directory, which is a real directory on the host, or one that was downloaded. It also refuses a Bundle opened by path that is not installed, for a daemon is never run once. Without this a copy with another `bin/` would be started outside the sandbox on the installed one's consent and no question. And `Bundle::open` holds the daemon's executable to more than the application's: a regular file inside the Bundle with the executable bit, an x86_64 ELF, and no symlink on its path, so a link out of the Bundle, or to a place the application can write, is not followed. The Bundle's own directory is not writable from the sandbox, which sees it read-only.

**What the application sees.** The socket, as a file bound into the private runtime directory at the same relative path, read-write, and nothing else of the host's runtime directory. Connecting needs no right Landlock handles; the bind is the grant, as the Wayland socket's is. If the socket is not there when the application starts, the application starts without it and `oma run` says so on standard error. The Bundle's executables are already runnable from `/app` (the baseline allows execution there), so a helper such as `ratmos serve` needs no permission of its own.

**Bundles hold what the daemon runs.** `oma bundle` takes `--include <file>[=<path in the Bundle>]`, repeated, and copies each regular file into the Bundle, keeping its executable bit, refusing a path outside the Bundle, a symlink, a name that is already taken, and the Manifest's own files. This amends ADR 0032's "extra resources are copied by hand", which `oma inspect` still checks afterwards. `Bundle::open` checks the daemon's executable the way it checks the application's.

This amends ADR 0012, whose vocabulary was closed until a new ADR; ADR 0005, whose deny-by-default sandbox now has one declared exception, for a program the user has been told runs outside it; ADR 0023, whose record gains one entry; and ADR 0032. It does not change ADRs 0010, 0024, 0025 or 0034.

**What it costs.** A Bundle with a daemon is only as confined as the daemon. The sandbox still limits the application, but an application that can reach the daemon's socket can ask it for whatever it answers, so the user is trusting the Bundle's author with their account, and the consent line is the whole of the protection. There is one daemon, so one version of it. Upgrades are not built (`oma install` refuses an Identifier that is installed), so what happens to a running daemon when a Bundle is replaced is for the ADR that builds them; a daemon that leaves when its binary is replaced, as Atmos's does, and a socket unit that starts the next one, is what this design would want. A daemon that takes the session's environment from its clients, as Atmos's does, takes the application's sandboxed one unless the application says it has none; that is the application's to handle, and a daemon that does is the same one a Bundle without a sandbox would need. Nothing registers the daemon at install time (`.desktop` and unit registration are not built); starting at `oma run` is enough for now.

**Rejected.** A bare permission for a socket path, which leaves the daemon to be installed by some other means and makes the sandbox boundary depend on the daemon distrusting its clients' environment; a second socket for sandboxed clients, which the user ruled out; running the daemon inside the sandbox with wider grants, which would need grants (the home directory, `sudo`, Hyprland's socket) that ADR 0012 rules out for every application; and a permission for executing a helper from the Bundle, which the baseline already allows.
