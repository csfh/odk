# An upgrade is a higher version of the same Identifier, offered through a per-application inbox

omalaunch has no update API (ADR 0010). An application that wants to update itself stages the new Bundle directory in its own inbox, `~/.local/share/oma/inbox/<identifier>/`, using the `updates` permission (ADR 0012). Applications are never given write access to `~/Applications`, because a Bundle is a directory (ADR 0022) and write access there would let one application overwrite another's ELF in place and run with its permissions, with no consent prompt because the permissions would not change.

An application writes the staged Bundle into `<name>.oma.stage/` inside its inbox and renames it to `<name>.oma/` when it is complete. A rename within one filesystem is atomic, so omalaunch never sees a half-written Bundle, and it ignores everything in an inbox that does not end in `.oma`. Path units do not watch recursively, so each installed application gets a template path unit instance, `oma-inbox@<identifier>.path`, that watches its own inbox; registration enables and disables these (ADR 0009). This was tested on the development machine with a transient user path unit: `PathChanged=` on a directory fires when a direct child is created or renamed into it, including the `.oma.stage` → `.oma` rename, but not for writes inside a subdirectory, which is why each inbox needs its own watch. Creating the `.oma.stage` directory also fires it, which is harmless because `omalaunch --register` ignores anything not ending in `.oma` and is idempotent.

omalaunch first moves each staged Bundle out of the inbox into a directory only it can reach, so the application cannot change it while it is being checked, and accepts it only if its Identifier equals the name of the inbox it arrived in, its version is higher than the installed one, and its Manifest is valid. A staged Bundle that fails these checks is deleted. The sandbox exposes only that application's own inbox, so the inbox name cannot be forged, and an application can offer a new version of itself but never of another application.

An accepted Bundle takes effect immediately: omalaunch moves the old directory to the previous-version store (ADR 0011) and places the new one in `~/Applications`. A running instance is expected to keep running the old files, since its sandbox already holds them, and the new version is used from the next launch. If the new version requests any permission missing from the consent record (ADR 0023), it does not launch until the user consents. If the user declines, the consent dialog offers "Keep previous version", which rolls back (ADR 0011) and launches the old version, so declining never leaves a dead application. A user dropping a higher version into `~/Applications` by hand is treated as an upgrade too, matched by Identifier and not by directory name.
