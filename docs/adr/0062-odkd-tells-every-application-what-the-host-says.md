# `odkd` tells every application what the host says

ADR 0044 gave a sandboxed application the user's text size and font as a copy that `oma` writes and mounts where the real files are, and rejected "a resident `oma`, or a socket-activated one, telling applications" as a protocol, a client and a socket for two values that a file carries. ADR 0048 then made the user's request for reduced motion Hyprland's `animations:enabled`, which only Hyprland knows and a sandbox must not reach. It first put a third value in the copy, a `[motion] reduced` key read where `OMA_SANDBOX=1`, and on 2026-10-25 the user took that out: a sandboxed application is told nothing about motion, and the source that will tell it was left to be decided. The same day the user said that ODK should run an `odkd` that answers this: **a per-user daemon on the main system, not sandboxed, that provides everything an application needs to know from outside its sandbox.** This record is the choices made on their behalf, and is open to change.

**The daemon.** `odkd` is a program of ODK's. It runs as the user, outside every sandbox, with the user's session, and it reads what ODK applications follow: Hyprland's `animations:enabled` by the rules of ADR 0048 (the instance is found from `HYPRLAND_INSTANCE_SIGNATURE` or the newest `$XDG_RUNTIME_DIR/hypr` directory that answers, `.socket2.sock` announces `configreloaded>>`, the wait doubles from 200 ms to 5 s), the text size by the rules of ADR 0043 (`[font] base-size` of `~/.config/omarchy/shell.toml` over the theme's, 9 to 20, 12 by default), and the monospace family fontconfig gives (`fc-match`, which reads `~/.config/fontconfig/fonts.conf`). It watches the directories those files are in, so a rename over a file is seen. The theme's colours too, as Omarchy has them and not converted: the entries of the theme's `colors.toml`, the mode included. ODK reads nothing else of a theme for colour (ADR 0047), so `shell.toml`'s control colours are not sent. `odk-theme` in each application keeps turning the palette into ODK's colour tokens, so the rules for that stay in ODK's library and `odkd` only reads and sends. The user decided on 2026-10-26 that colours are in the first version.

**The font** is sent as the family name only, and each application finds the font itself, as ADR 0043 has it. The user decided this on 2026-10-26.

**The protocol.** One stream socket, `$XDG_RUNTIME_DIR/odk/odkd.sock`. A client connects and sends nothing. `odkd` writes the whole state as one line of JSON, `{"v":1,"motion":{"reduced":false},"text":{"base_size":12},"font":{"family":"JetBrainsMono Nerd Font"},"colors":{"mode":"dark","background":"#0D0C0B","foreground":"#E8E0D4",…}}`, and writes the whole state again, as a new line, whenever any of it changes. It reads nothing from the client and ignores what is sent, closes a connection that sends more than a small bound, and caps the number of connections. A value it cannot read is absent from the line, not guessed: an application treats an absent value as the ADRs say (motion is not reduced, the scale is 1, the font is the application's own, the palette is ODK's built-in one). There is nothing to ask, nothing to write and nothing to run, so a client that is hostile can only hear what every application hears.

**Starting it.** `odkd` is installed for one user, by the install script (run with curl) and without root: the program in `~/.local/lib/odk/odkd` and two `systemd --user` units, `odkd.socket` and `odkd.service`, in `~/.config/systemd/user/`, enabled for that user with `systemctl --user enable`. The socket exists from login and the first connection starts the daemon. The user decided this on 2026-10-26. The program is private and never on `PATH`: `odk` stays the only command, and `odkd` is not one of its subcommands. The units name the program with `%h`, so they hold no user name. `odkd` holds no state it cannot read again, so it may be stopped and started at any time.

**Who asks.** Every ODK application, sandboxed or not, asks `odkd` through `odk-theme`, and nothing else. There is no second path for an unsandboxed application, no read of `shell.toml` for `[font]`, and no connection to Hyprland from an application. An application that finds no socket, or none that answers within a short wait, runs with the defaults above. `ODKD_SOCKET` names another socket, and `ODKD_SOCKET=none` says there is no host, so that a test, a screenshot or a build machine never hears the user's own settings. The application's own choices (`odk::ui::set_reduced_motion`, `FontConfig`) still add to what the host says.

**The sandbox.** The baseline gains one row: the directory `$XDG_RUNTIME_DIR/odk/` is bound read-only into the sandbox's private runtime directory at the same path, for every application and with no permission to ask for, because the socket in it can say only what the user's settings are. The directory is bound and not the socket, so that a socket systemd makes again is the one the application sees. A user with no `odkd` has no such directory, and the bind is left out. The sandbox mounts nothing of `~/.config/omarchy` or `~/.config/fontconfig`. The Hyprland socket is still never granted (ADR 0048). `oma` does not depend on ODK (ADR 0013): it knows the socket's path and binds it, and nothing else of `odkd`.

**What this replaces.** ADR 0044 is superseded: `oma omarchy sync`, the copy under `~/.local/share/oma/omarchy/`, `oma-omarchy.path` and `oma-omarchy.service`, and the two mounts go. ADR 0048 is amended: the question (Hyprland's `animations:enabled`) and the rule that a missing answer is not a request are unchanged; the transport changes, so that an application reads the setting from `odkd` and not from Hyprland, and a sandboxed application, which ADR 0048 leaves without an answer, gets one. ADR 0043 is amended: `odk-theme` takes the text size and the font from `odkd`, and the reading of `shell.toml` and `fonts.conf` moves to the daemon with its rules unchanged. ADR 0046 stays superseded. ADR 0035 is unchanged.

## Considered Options

- **Keep the copy (ADR 0044) and tell a sandbox nothing about motion (ADR 0048 as it stands).** Works for the text size and the font, and costs nothing, but a sandboxed application never reduces motion for the user, every new value is a key in a file that `oma` writes from sources it must also know how to read, a running sandboxed application sees a change only when a path unit fires, and an unsandboxed one has a different path than a sandboxed one.
- **Mount Hyprland's socket, or `~/.config/omarchy`, read-only.** The Hyprland socket accepts `dispatch`, so an application that could open it would not be sandboxed; the directory holds `shell.json`, hooks and plugins.
- **A resident `oma`.** `oma` is not a daemon (ADR 0025) and does not depend on ODK (ADR 0013); the knowledge belongs to ODK.
- **A daemon declared by each Bundle.** One per application, and each would read the host again.
- **The freedesktop settings portal, or D-Bus.** Nothing in Omarchy sets the keys (ADR 0046), and a sandbox has no bus.

## Consequences

- A change reaches a running application at once, sandboxed or not; ADR 0048's "as of its launch" is gone.
- A new program, two units and a protocol to keep: version `v` is 1, a client ignores keys it does not know, and `odkd` never removes one without a new `v`.
- A user who has not run the install script has no `odkd`, and so does a machine without `systemd --user`; applications there run with the defaults.
- `odkd` outside the sandbox answers every application the same, which is the point and also the limit: it cannot say one thing to one application and another to another. A setting that should differ by application is not for it.
- The socket is a file that systemd owns, so it outlives `odkd` restarting, and the directory bind means it need not even do that. A test connects from inside a sandbox through the bind.
- `docs/spec/sandbox-baseline.md`, `docs/spec/odk-foundation-tokens.md` ("Text size") and `docs/checks.md` change with it; the `db` feature and the other parts of ADRs 0046 to 0049 are unaffected.
- The socket path, `$XDG_RUNTIME_DIR/odk/odkd.sock`, was agreed by the user on 2026-10-26. No design point is open.
